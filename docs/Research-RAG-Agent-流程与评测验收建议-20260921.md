**3. 建议补的三个完整流程**

**流程 A：跨文档比较与带证据报告，作为首个主流程。**

示例输入：“比较项目内 A、B、C 三份材料的方法、实验设置和局限，判断哪种更适合我的低显存场景；每项结论给出出处。”

执行要求：

1. 根据项目内文档台账解析 A/B/C；同名、多版本或关键约束不清时才澄清。
2. 拆成有限个比较维度，记录需要回答的问题与现有证据。
3. 先检索定位，再用原文工具读取相关范围。后续工具参数必须能够来自此前观察，例如检索返回的 document_id 和页码。
4. 建立比较表：每个单元格关联证据；缺少条件的结果不能强行横向排名。
5. 检查必需维度是否缺证据。仅对缺口补检索或扩大原文范围，次数有上限。
6. 输出并保存 Markdown/结构化报告：比较表、推荐及理由、不可比项、未解决问题、来源定位。

完成条件：选对材料；覆盖用户要求的维度；重要结论有支持证据；证据不足处明确保留空缺；报告可重新打开。不能用“调用了八次工具”代替完成条件。

所需新增能力以 `list_documents`、有界 `read_document_range`、稳定证据注册表和报告保存为主。文档 outline 可以先复用现有 Markdown heading 和 PDF 页信息，不必先实现复杂版面理解。

**流程 B：连续追问、澄清与报告修订。**

示例：在流程 A 后，用户说“只保留你刚才说的后两篇；更关注部署成本；不要改动原有引用”。或者任务需要用户补充目标硬件，等待回答后继续。

执行要求：恢复 session 和先前报告；解析指代及新增约束；保留仍然有效的证据；只对新问题补操作；保存新报告版本与修改摘要。服务重启或断线后能查回状态。用户取消后，不再继续昂贵调用或产生新的写入。

完成条件：正确指代、遵守新约束、未丢失保留内容；waiting_user 与执行失败有明确区分；resume 不重复保存报告或其他副作用。

这个流程证明的是会话与任务状态管理，不需要引入跨会话语义记忆。

**流程 C：结论核查与有界补证，作为第二个效果场景。**

示例输入：“这段笔记说方法 B 在所有设置下都优于 A。请检查项目里的材料，指出哪些说法被支持、哪些冲突、哪些无法确认。”

执行要求：把待核查文本拆成可检查的陈述；检索及读取相应证据；给出 supported / contradicted / insufficient；对证据不足的陈述进行一次有界补查；输出修订建议与原文引用。发现检索无结果时允许改写查询、读取上下文或最终报告证据不足。

完成条件：区分“找到相关段落”和“段落支持这个陈述”；保留冲突证据；不将资料缺失当作结论为假；证据不足时不过度生成。

流程 A 与 C 共用证据检查机制，B 共用任务运行状态。优先复用这些核心模块，不需要为三个流程分别做三个 Agent。

**4. 最小运行与产品要求**

- Session 存用户消息、助手回复和顺序；Run 存当前目标、项目范围、状态、预算、输出；Step/ToolCall 存执行动作、结果引用、状态和计量。
- 每条证据绑定 document_id、文档版本/内容哈希、chunk 或原文范围、稳定 source_id。同一来源重复命中不产生相互矛盾的别名。
- 状态至少区分 running、waiting_user、completed、insufficient_evidence、failed、cancelled、budget_exceeded；状态名可由实施会话统一设计。
- 等待用户时间与实际执行时间分开统计；resume 后沿用剩余预算，不以反复恢复规避上限。
- 工具执行前、执行后和证据注册有明确 checkpoint。恢复允许重试读操作；写操作用持久化 operation_id/tool_call_id 去重，不能只用 run_id + 模型轮次，因为一轮可能包含多个写操作。
- 对失败调用允许有界修正或瞬时重试；对已完成的相同读调用可复用结果。不要把“参数相同”一律视为没有进展，也不要允许重复调用无限增长。
- 每轮上下文预算包括指令、工具 schema、历史和工具结果；保存完整结果，模型只接收需要的内容及可寻址引用。摘要不能替代最终事实核查的原文。
- UI 至少提供会话列表、项目/材料选择、当前任务状态、工具操作摘要、引用打开、报告保存/下载、澄清回复、取消/恢复。可以先沿用 Gradio，是否改 Vue 由岗位展示目标和工期决定。
- 展示实际动作和简短决策摘要即可；不将模型长篇“思考”当作正确性或可靠性的证明。

**5. 评测必须前置，拆成三层**

第一层：确定性的协议与恢复测试。使用 fake 模型/工具，检查事件顺序、引用映射、scope、失败处理、幂等和预算。它证明程序行为，不证明真实模型效果。

第二层：真实服务集成。真实 embedding、检索库、reranker、LLM 上验证摄入→检索→读取→回答→报告。当前 live 测试主要检查 HTTP 成功、非空检索和 invalid IDs 为空，尚不能证明答案正确或实际用了多步工具。

第三层：冻结任务集上的真实模型效果。以任务完成、事实支持和成本为主，工具数与规划次数只做诊断。

**6. 数据集与基线**

建议从 20 条开发任务和独立 60 条留出任务起步。以下是预算有限时的启动分布，不保证统计充分性：

| 留出任务类型 | 初始数量 | 作用 |
|---|---:|---|
| 简单单证据 QA | 10 | 检查新系统是否让简单任务变慢或退化 |
| 跨文档比较 | 20 | 主流程收益 |
| 多轮指代、澄清、修订 | 10 | 会话状态与交互 |
| 陈述核查 | 10 | 支持/冲突判别与补证 |
| 无答案、缺字段或不可比场景 | 10 | 校准拒答与不确定性表达 |

至少使用多个主题/文档组。避免近重复题跨开发/测试集；评测中检索使用共享完整语料快照，不要给每题只提供两份人工筛好的候选。留出题冻结后不再用其反复调 prompt；若修改，建立新版本并保留原结果。

每条任务应包含：task_id、family、项目/文档范围、用户输入或多轮脚本、要求的输出字段、关键事实、可接受证据集合、预期边界行为、人工判分 rubric。不要把唯一工具序列当 gold；多条有效路径都应被接受。

多轮任务若用用户模拟器，固定可披露信息与回答策略，不能让模拟用户泄露标准答案。

至少比较三组：

- B0：固定单步 Hybrid RAG，使用相同历史与预算，作为强基线。
- B1：修复 P0 正确性问题后的当前 bounded tool loop，作为已有能力基线。
- B2：新任务流程与证据补查。

同一模型与参数、相同语料/检索设置、相同任务与可访问历史、相同最大预算。若比较控制流程，工具集与证据格式也要一致；若比较整体产品，明确工具集差异，不把总收益都归因于某个模块。不能用已知引用 bug 的旧版本来夸大新系统收益。

有余力时只增加一个消融：B2 关闭证据缺口补查。先回答“补查是否帮助了多证据任务”，再决定是否加入更多反思或规划模块。

**7. 指标定义**

| 指标 | 计算口径 | 用途与注意事项 |
|---|---|---|
| 任务成功率 | 满足该任务全部必需条件的任务数 / 全部任务数 | 主指标；正确事实、关键约束、必需输出与引用要求共同判定；超时失败计入分母 |
| 子要求覆盖率 | 完成的必需子要求数 / 所有必需子要求数 | 辅助解释部分完成，不能代替严格成功率 |
| 事实支持率 | 被原文支持的事实陈述数 / 生成的可核查事实陈述数 | 防止“有引用但不支持”；同时检查关键事实覆盖，避免只输出极少陈述得高分 |
| 引用有效率 | source_id 可解析、来源/版本/范围匹配的引用数 / 全部引用数 | 程序正确性；无引用输出单独判定，不能算作自动满分 |
| 引用覆盖率 | 必须引用且有支持性引用的陈述数 / 所有必须引用的陈述数 | 与事实支持率分开统计 |
| 无答案正确处理率 | 无答案任务中正确表示资料不足且未编造答案的任务数 / 全部无答案任务 | 同时报告可回答任务的误拒答率 |
| 核查分类效果 | supported/contradicted/insufficient 的混淆矩阵与 macro-F1 | 不能只看多数类别准确率 |
| 工具错误与恢复 | 参数/超时/范围/供应商等错误次数；成功恢复任务数 / 注入可恢复故障任务数 | HTTP 200 不等于任务成功；读工具空结果不一定是工具失败 |
| 检索 Recall@K | 每题命中的相关证据数 / 该题全部 gold 证据数，再按预声明方式汇总 | 多证据题不能以“任一命中”替代 Recall；可并列 HitRate@K、MRR |
| 延迟 | 客户端任务开始到最终结果的 P50/P95；另列模型、检索、重排、工具与排队耗时 | 单列用户等待时间；披露并发和失败任务时长；不要把检索耗时当端到端耗时 |
| 成本 | 每次运行总 input/output token、实际调用费用；总费用 / 成功任务数 | 包含规划、补查、重试、失败、降级；建库/摄入成本另列；unknown usage 不能记成 0 |

当前 `evaluate_retrieval.py` 使用 local 64 维哈希向量、内存存储与 local 重排；示例集只有两题。`hits[k]` 统计任一 gold 命中，实际是 HitRate@K；每题只有一个 gold 时才与 Recall 一致。该脚本保留为快速回归，新增真实任务评测入口。

**8. 建议的首轮验收门槛**

下面是供下一会话评审的工程目标，不是现有结果，也不是行业统一标准。正式运行留出集前冻结目标；不要为了通过验收事后调低门槛。

| 类别 | 建议门槛 |
|---|---|
| 确定性正确性 | 引用映射、合法工具消息配对、scope 边界、状态转换、预算和错误分支 fixtures 全部通过；串号 0、越界取证 0 |
| 恢复与幂等 | 指定 checkpoint 注入重启/重复 resume 后，最终输出一致且重复副作用为 0；取消后无新增写入 |
| 真实任务成功 | 初始目标总体 ≥80%，各任务类别独立报告；不可仅用多数简单题提高总体值 |
| 事实与引用 | 事实支持率 ≥95%，引用覆盖率 ≥90%；运行内来源映射错误为 0 |
| 无答案处理 | 正确处理率 ≥90%；可回答任务误拒答率 ≤10% |
| 相对收益 | 多文档任务相对强基线争取 +10 个百分点；未达到时分析任务子类和成本，不承诺一定提升 |
| 简单任务开销 | 简单 QA 的 P95 初始目标不超过 B0 的 1.3 倍；复杂任务先按预定预算显式结束，不预设脱离模型条件的绝对时延 |
| 成本收益 | 可先以 B2 平均任务成本 ≤B0 的 2 倍为设计约束；必须与成功率一起比较。较高成本若无任务收益，应缩短执行路径 |

60 个留出任务只能做起步评估。报告成功数/总数和不确定性；“提升 10 个百分点”不自动意味着统计显著。使用配对任务比较，可按任务/文档组 bootstrap；重复运行不能作为完全独立的新任务放大样本量。样本较少的子类不要宣称可靠的总体概率。

判分优先自动验证可确定的部分，再由人工核对事实与证据。可使用固定版本、固定 rubric 的 judge 辅助，但应盲化系统名称，并人工审阅全部争议样本及一部分其余样本。模型自评不能成为唯一正确性来源。
