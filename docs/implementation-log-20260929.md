## 发现的问题与解决方法

### 1. 去重上传后项目范围丢失

同一内容上传到第二个项目时，PostgreSQL 已补充项目关联，但内存向量索引仍只保留首次上传的 `project_ids`，导致第二个项目搜索为空。

解决：去重分支提交新项目关联后，读取已有 chunk，并同步更新内存索引的项目范围；不重复解析、Embedding 或创建向量。这个修复体现了“数据库事实与索引副本一致性”的处理思路。

### 2. hydration 对测试替身返回形状过于严格

真实 SQL 查询返回 `(Chunk, Document, project_id)`，旧测试替身返回 `(Chunk, Document)`，导致解包异常。

解决：兼容两种行形状，并在旧替身场景使用当前请求项目作为归属。生产查询仍以数据库关联为准。

### 3. 失败报告恢复时发生非幂等变化

报告保存事务失败后，checkpoint 中应保留模型原始报告，供恢复时零新增推理重试。此前模型缺省字段被 Pydantic 补入 `change_summary`，并且恢复路径再次给 usage 添加 `usage_status`，造成恢复前后状态不一致。

解决：checkpoint 保存 `submit_report` 的原始参数；只在报告渲染/持久化时使用校验后的模型；恢复已完成 checkpoint 时不重复计价或改写 usage。结果是失败可见、恢复幂等，且不需要重新调用模型。

## 可用于面试的真实材料

- 困难点：去重上传跨越 PostgreSQL 文档台账和向量索引两个一致性边界，单看上传接口返回成功并不能证明检索可见。
- 困难点：故障恢复不仅要“能继续”，还要保证 checkpoint、报告正文、引用和 token 账本不被恢复动作悄悄改写。
- 解决方法：先用离线回归定位最小失败样本，再分别修正索引同步、兼容性边界和幂等语义，最后以完整回归验证。
- 可量化结果：4 个失败全部修复；回归从 184 passed / 4 failed 提升到 190 passed / 6 skipped；未消耗真实模型额度。
