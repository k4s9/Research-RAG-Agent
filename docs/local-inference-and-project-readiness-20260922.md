## 为什么 256K 仍可能“预算耗尽”

此前四次 `context_tokens` 是**应用在发送请求前主动停止**，不是模型服务报上下文超限。
当时 24,000 采用序列化 UTF-8 字节上界，明显不同于真实 tokenizer 的 24,000 token。
因此不能把那些失败解释成“六份短文档已经超过模型 256K”。

三个量独立：服务单次输入+输出窗口；应用每次输入上限；整轮累计预算。
例如六次调用各消耗 30K token，每次都远小于 256K，但累计 180K 会超过整轮 128K。
工具次数、返回字符和时间也各有独立上限，终止原因需要分别报告。
本地部署可以无按次 API 账单，但仍有算力、显存、耗时和电耗，不能据此将运行成本记为零。

## 是否已经是 RAG Agent

是，可以准确称为“基于 RAG 的单 Agent 科研助手原型”。当前具备：

1. 模型通过原生工具调用选择检索、文档发现、原文读取及后续动作。
2. 工具返回观察后进入下一次决策；参数错误和证据缺口可反馈给模型。
3. 多轮会话、run/checkpoint、稳定来源编号、预算与失败轨迹。
4. 比较报告、澄清、修订及有界核查接口和相应离线流程验收。

已有真实轨迹也显示模型主动选择了 list_documents/search_knowledge 及查询参数。
不必以多 Agent、自动长期记忆或固定最少步数作为 Agent 定义。
目前定位仍是原型：完整真实报告交付未验收，不能称成熟可靠的科研助手。
