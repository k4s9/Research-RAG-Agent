## 接下来按顺序完成

### 1. 优先验收修复后的全自动闭环

核对已有代码和失败轨迹，准备一个新版本的小实验，明确任务数、模型调用、token、时间和
辅助模型预算。先做 1 条比较与 1 条修订，覆盖明确的不可比条件和能耗缺测；要求自然
保留未知结论，自动保存，重新打开，逐条核对出处，全程不靠手工恢复产物。

初始场景可沿用现有合成语料定位回归，但随后必须加入真实材料；不要把同一例反复调试当作
泛化效果。对漏字段、finish_reason、实际输出达到 2,048 的情况保留全部原始响应。
不得通过放宽校验、删除失败、重置 checkpoint 预算或静默补全模型字段制造成功。

### 2. 验证实际使用可靠性

在主流程稳定后，以 5 个代表场景各重复 2 次作为起步演示验收：跨文档比较、澄清修订、
无答案/证据冲突、取消、恢复。定义每个场景的预期状态，不能把正确取消当作失败。
要求无需人工救场，报告、引用和预算不丢失；这是 10 次场景检查，不是统计稳定性证明。

补做浏览器交互、PostgreSQL 迁移和重启检查。当前向量只在内存中，若要在简历上声称
Milvus 持久检索，必须实际接通并验证重启。已有测试 Compose 尚未证明部署可用。

### 3. 处理真实服务问题

最近只读检查中 Reranker 仍缺 `--chat-template`，Top-3 曾漏掉 Beta，由模型按 ID 读取补齐。
先复核现在的部署状态。诊断方案见 `docs/reranker_deployment_diagnosis_20260921.md`。
外部模型容器的修改/重启尚未获得执行授权；如需操作，先准备具体差异、复验及回退步骤。
不要把协议可调用当作排序质量合格。

### 4. 小规模对照与量化

先准备 10–20 条人工核对的开发题，覆盖问答、比较、核查和无答案，再冻结独立测试题规模。
同模型、语料和明确预算下比较 B0 强单步 RAG、B1 既有工具循环、B2 研究报告流程。
不立即扩大到 80 题；20 开发 / 60 留出仍是待评审建议。

起步验收目标（不是当前成绩，也不是行业统一标准）：完整任务成功率 ≥80%，事实支持率
≥95%，有支持证据的引用覆盖率 ≥90%，无答案处理正确率 ≥90%。检查推荐理由中的事实；
同时报告分子/分母、全部失败、误拒答、完整任务 P50/P95 和 token，费用未知时记 unknown。
来源串号和测试中的数据丢失应为 0。原文引用匹配不是自动语义正确，模型自评不代替人工评分。

完成稳定演示、可靠性和对照证据后，再完善 README、演示素材与简历表述。
目前适合称“有真实运行证据的 RAG Agent 原型”，不要称全自动稳定生产系统。
